<objective>
Wire the three-stage pipeline into the Orchestrator (D-02, ORCH-01/ORCH-03): construct the agent registry + OmX + OmO + Clawhip in `__init__`, and restructure `process()`/`process_stream()` to run OmX.plan() → OmO.dispatch() → ResponseComposer instead of the current LLM-completion-only path — while preserving the exact async-generator streaming contract ws_handler.py depends on.

Purpose: This is the integration seam that turns everything built in Waves 1-3 into the operator-visible behavior change. RESEARCH.md Pattern 4 gives the minimal-diff restructuring: the chat reply stops being "whatever Claude free-associated" and becomes a report of what actually executed. On OmXPlanValidationError (or a scope/plan rejection), the operator sees a PLAN_REJECTED event via clawhip — never a dispatched partial plan.
Output: rewired orchestrator.py (both entry points) + an end-to-end integration test.

**D-02a note (deliberate supersession — read before implementing):** `Orchestrator.__init__` continues to construct `LLMRouter`, `InstructionParser`, `EngineRouter`, `ToolSelector`, and `ResponseComposer` (these remain instantiated to avoid a wider refactor), but per D-02a (03-CONTEXT.md) the new pipeline does NOT call `InstructionParser.parse()`, the standalone `EngineRouter.dispatch()`, or `ToolSelector` — OmX's LLM DAG generation supersedes all three (it decomposes the operator directive into engine/agent/tools directly, and OmO passes `Directive.tools` straight to `BaseAgent.execute()`). Only `LLMRouter` (via OmX) and `ResponseComposer` are live callers in the new path. Do NOT wire `parse()`/`dispatch()`/`ToolSelector` into process()/process_stream() to "use" them — their remaining uncalled state is an intentional architectural choice, not an oversight. (`ResponseComposer` gets its first real caller here via compose_plan_summary.)
</objective>
