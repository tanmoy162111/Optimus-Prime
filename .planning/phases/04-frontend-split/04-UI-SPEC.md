# Phase 4 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope note:** This phase is a componentization refactor of an existing, already-styled dashboard (`frontend/src/App.jsx`), not a redesign. Every table below documents the design system that **already exists and must be preserved unchanged** across the extraction into `frontend/components/*.jsx`, plus the handful of UI states that are genuinely new in this phase: the error-boundary fallback (UI-02) and the chat connection/handshake states exposed by the `ChatPane.tsx` rewrite (D-01/D-02/D-03). No new colors, type sizes, or spacing values are introduced.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none — hand-rolled Tailwind + custom `@layer components` classes in `frontend/src/index.css`; no shadcn or component library was ever introduced and none is being added in this phase |
| Preset | not applicable |
| Component library | none (raw Tailwind utilities + custom classes: `panel`, `panel-header`, `label-xs`, `input-field`, `btn-primary`, `btn-ghost`, `dot-live`, `severity-*`) |

| Font | `Geist` (sans, body/UI text) + `Geist Mono` (`font-mono`, used for all labels, data, timestamps, badges, code-like content) — loaded via Google Fonts `<link>` in `frontend/index.html`, declared in `tailwind.config.js` `theme.fontFamily` |

Extracted `.jsx` panel files and `ChatPane.tsx` MUST import/apply these same classes verbatim — do not introduce parallel styling (no inline `style={{}}` color values, no new Tailwind color utilities outside the existing zinc/emerald/red/amber/sky/orange/yellow/blue palette already in use).

## Spacing Scale

Declared values — this is the actual scale already in use across `App.jsx`, carried over unchanged (Tailwind's default 4px grid):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-label gaps (`gap-1`), dot indicators |
| sm | 8px | `gap-2`, compact stacks between panels (`gap-2 p-2` on the main grid) |
| md | 12px | `px-3 py-2` panel-header padding, `input-field` padding, chip padding |
| lg | 16px | `px-4 py-3` chat message-list padding, `panel` internal content padding |
| xl | 24px | `px-6` logo block separation in `StatusBar` |
| 2xl | 32px | not currently used in this dashboard — reserve if a new full-width section is ever added |
| 3xl | 48px+ | not used — this is a dense operator console, no page-level whitespace sections |

Exceptions: 12px (`px-3`/`py-2`/`py-3`) is the dominant panel padding value throughout the existing codebase and is NOT a deviation to normalize — preserve exactly as-is in every extracted file.

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Label (`label-xs`) | 10px | 600 (semibold) | ~1.2, `tracking-[0.08em]` uppercase, color `text-zinc-500` |
| Data / status / mono (`text-xs`) | 12px | 400 regular (500 medium on a few status values) | 1.4 default |
| Body (chat messages, inputs) | 14px (`text-sm`) | 400 regular; `font-medium` (500) reserved for the user's own chat bubble only | 1.625 (`leading-relaxed`) |
| Heading | n/a — this dashboard has no page-level headings; `panel-header` uses the 10px `label-xs` style as its "heading" | — | — |

Contract: 2 primary weights — regular (400) and semibold (600, via `font-semibold`). Weight 500 (`font-medium`) is a pre-existing, narrowly-scoped exception used only for the operator's own chat message text (`ChatMessage` when `isUser`) — preserve that one usage, do not expand medium weight to new elements.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `zinc-950` (`#09090b`) / `zinc-900` | App background (`bg-zinc-950`), panel headers (`bg-zinc-900`) |
| Secondary (30%) | `zinc-900/80` with `zinc-800` borders | Panel bodies (`.panel`), `input-field` fill (`zinc-800`), chip backgrounds |
| Accent (10%) | `white` (`#fafafa`) | Reserved for: `btn-primary` background (Send button, primary form submits), `StatusBar` brand mark (Shield icon + "OPTIMUS PRIME" wordmark), the operator's own chat bubble background |
| Status accent (live/success) | `emerald-400` | Reserved for: `dot-live` pulsing indicator, `StatusBar` "ok" dots, connected/session-ready states, engagement timer text — do not repurpose for any other state |
| Warning | `amber-400` | Reserved for: pending human-gate indicator ("gate awaiting") only |
| Destructive/error | `red-400` / `red-500` | Reserved for: disconnected indicators, chat error bubbles (`isError`), `severity-critical` badges, the gate "skip" action |

Accent reserved for: primary Send/submit buttons, the brand mark, and the operator's own chat message bubble — never used for panel chrome, borders, or informational text.

This is a 4-color semantic system (accent white / live emerald / warning amber / destructive red) layered on a neutral zinc scale — preserve all four exactly; do not consolidate or introduce new hues.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | Send button — icon-only (`Send` lucide icon, no label), existing `btn-primary`. Unchanged by this phase. |
| Empty state heading | "Ready for operator input" (existing chat empty state, `ChatPane.tsx` must reproduce verbatim) |
| Empty state body | "Try: `$recon` or `$pentest`" (existing hint text below the heading, monospace inline chips styled the same as directive hint chips) |
| Error state — chat handshake failure (NEW) | If the server never responds to the `init` message with a `session` ack (timeout or explicit `{type:"error"}`), inject one system `ChatMessage` with `type: 'error'` (reuses existing red bubble: `bg-red-500/10 border-red-500/30 text-red-300`): **"Couldn't start a session with the backend. Retrying automatically — check that the backend is running."** Do not spam this message on every reconnect attempt; show it only once per handshake failure, not per WebSocket retry cycle. |
| Error state — panel crash (NEW, error boundary) | Heading: **"This panel crashed"**. Body: **"An unexpected error stopped rendering. Other panels are unaffected."** Action: **"Reset panel"** button. |
| Destructive confirmation | Human gate "skip" button: no confirmation dialog — existing one-click behavior (`btn` styled red, immediate action on click). Preserve as-is; adding a confirm step is out of scope for this phase (not in CONTEXT.md decisions). |

## New UI Surface: Error Boundary Fallback (UI-02)

Applies to every extracted panel (`StatusBar`, `ScopePanel`, `DirectivesPanel`, `TerminalPanel`, `FindingsPanel`, `AgentTracker`, `PlanPanel`, `HealthPanel` — per D-05, all of them, not just the 3 ROADMAP-named panels). Implementation shape is Claude's discretion (class component vs. shared `ErrorBoundary.jsx`), but the rendered fallback markup and copy are locked here so the grid never visibly breaks or reflows:

```
<div className="panel flex flex-col h-full">
  <div className="panel-header">
    <div className="flex items-center gap-2">
      <AlertTriangle size={13} className="text-red-400" />
      <span className="label-xs text-red-400">{panelName} — Error</span>
    </div>
  </div>
  <div className="flex-1 flex flex-col items-center justify-center text-center px-4">
    <AlertTriangle size={22} className="text-red-500/60 mb-3" />
    <p className="font-mono text-xs text-red-400">This panel crashed</p>
    <p className="text-xs text-zinc-600 mt-1">An unexpected error stopped rendering. Other panels are unaffected.</p>
    <button className="btn-ghost text-xs px-2 py-1 mt-3 gap-1.5" onClick={resetErrorBoundary}>
      <RefreshCw size={12} /> Reset panel
    </button>
  </div>
</div>
```

Rules:
- The fallback keeps the exact `panel` / `panel-header` shape of a normal panel so the grid layout (widths, `flex`/`min-h-0` sizing) does not shift when one panel errors.
- Uses only existing color tokens (`red-400`/`red-500`, `zinc-600`) and existing icon set (`AlertTriangle`, `RefreshCw`) — no new visual language.
- "Reset panel" re-mounts the boundary's children (retry), it does not reload the page.

## New/Changed UI Surface: Chat Connection States (ChatPane.tsx rewrite — D-01/D-02/D-03)

The rewrite changes the underlying transport (raw `WebSocket` + `init`/`session` handshake replacing the non-functional Socket.IO client) but MUST reuse the exact visual states already established in the current inline `ChatPanel` — only the semantics of "connected" change (see below), not the markup or colors.

| State | Trigger | Visual (reuse existing markup verbatim) |
|-------|---------|------------------------------------------|
| Connected / ready | WebSocket open AND `{type:"session"}` ack received from server | Header: `<span className="dot-live" />` (pulsing emerald dot), no text label. Input enabled, placeholder `"Type a directive or message..."`. Send button enabled when input is non-empty. |
| Connecting / reconnecting / handshake-pending | WebSocket not yet open, OR open but no `session` ack received yet, OR closed and backing off | Header: red dot (`bg-red-500`) + `"disconnected"` text (`font-mono text-xs text-red-400`). Input disabled, placeholder `"Reconnecting..."`. Send button disabled. |
| Handshake failure | Server responds with an explicit error after `init`, or no `session` ack within a reasonable timeout | One-time system `ChatMessage` (`type: 'error'`, red bubble) per the Copywriting Contract above, in addition to the "disconnected" header state |

Critical semantic change to carry into `SessionContext` (D-07) and `StatusBar`'s `wsChat`/`chatConnected` prop: **"connected" must mean session-acknowledged, not merely socket-open.** Sending a `{type:"chat"}` message before the `session` ack is the exact bug this phase fixes (D-02) — the visual contract above exists specifically to prevent the operator from typing into a socket that looks live but hasn't completed the handshake. `StatusBar`'s existing `CHAT` status item (`READY` / `DISCONNECTED`, emerald/red dot) is unchanged visually — only wire it to the redefined boolean.

Feature parity to preserve unchanged in the rewrite (per D-02, "specifics"): plan display card (`isPlan` sky-500 bordered bubble with `Layers` icon header "ENGAGEMENT PLAN CREATED"), gate confirm/skip buttons (emerald/red pill buttons in the panel header when `pendingGate` is set), directive hint chips (`$recon` / `$pentest` / `$cloud-audit` / `$scope-discover`), and the token/model metadata footer line under assistant messages (`{tokens} tokens · {model}`, `text-zinc-600`).
