## 1. System Classification

**System Type:** Multi-Agent (Hybrid — LLM-driven plan decomposition (OmX) + sequential agent dispatch coordinator (OmO))

**Description:**
This system turns a single operator's natural-language directive (e.g. "audit acme.com — cloud + app security, stealth mode", or a `$pentest` keyword) into a supervised, multi-agent penetration-test execution run. OmX (the planner) asks Claude to decompose the directive into a structured, dependency-ordered DAG of directives — each naming a phase, an engine (Infrastructure / ICS / AI-ML), a sub-agent, a target, and a tool list, scoped by the operator's approved `ScopeConfig`. OmO (the coordinator) then walks that DAG sequentially (D-08: no parallel dispatch this phase), invoking each `BaseAgent.execute()` in turn, tracking `EngagementState.phase_status`, and reporting a whole-directive `PHASE_FAILED` event (with the underlying error) the moment a directive's sub-agent or tool call fails — instead of the current silent-drop behavior. clawhip (the router) keeps the sub-agents' own execution context free of delivery concerns: it is the only thing that formats and pushes lifecycle/finding/phase events to the frontend WebSocket and the XAI audit trail. The sole user is the operator watching the chat UI live; "good" looks like: every directive the operator did not explicitly scope is never silently executed, every phase failure is visible in the UI the moment it happens (not discovered later via a missing report section), plan generation never dispatches a hallucinated agent/engine/tool name, and a backend restart mid-engagement resumes from the last persisted `phase_status`/findings rather than losing the run.

**Critical Failure Modes:**
<!-- The 3-5 behaviors that absolutely cannot go wrong in this system -->
1. **Scope creep via OmX plan generation** — OmX's LLM-generated DAG includes a directive whose `target` falls outside `session.scope.targets` or inside `session.scope.exclusions` (e.g. Claude infers a related subdomain and adds a directive against it unprompted). Because OmO executes directives that can run real exploit tooling over SSH against a Kali box, an unscoped directive is not a cosmetic bug — it is an unauthorized-access risk against a system the operator never approved.
2. **Silent phase failure (the exact defect this phase exists to fix)** — a sub-agent/tool call inside a directive throws, times out, or returns a malformed result, and OmO does not emit `PHASE_FAILED` over the WebSocket. The operator believes the phase succeeded (or the engagement silently stalls) and only discovers the gap later, e.g. a missing report section with no explanation (ORCH-01).
3. **Malformed/hallucinated DAG dispatched as if valid** — OmX's structured-output call returns a directive referencing a non-existent agent name, an invalid engine, or a `depends_on` cycle, and OmO executes it anyway (crashing the session, dispatching to the wrong engine, or hanging on an unresolvable dependency) instead of failing plan validation before any tool ever runs.
4. **Directive execution out of declared DAG order** — a directive with unmet `depends_on` (e.g. an exploit directive) runs before its prerequisite (e.g. the verification/approval gate or recon phase) completes, producing exploitation activity the operator has not yet reviewed/approved.
5. **Session persistence corruption or stale resume** — the SQLite-backed `SessionStore` (PERSIST-01) loses or partially writes `phase_status`/findings under a WAL-mode write mid-directive (e.g. backend crash between two `INSERT`s), and on restart the operator resumes an engagement whose on-disk state does not match what actually executed against the target.

## 1b. Domain Context

> Researched by `gsd-domain-researcher`. Grounds the evaluation strategy in domain expert knowledge.

**Industry Vertical:** Authorized offensive security / penetration testing tooling (not a consumer or customer-facing AI product — a single-operator internal tool that dispatches real security tools against real, scoped infrastructure).

**User Population:** One operator (the pentester running the engagement) per `CLAUDE.md`/`PROJECT.md` — "Single operator, no auth hardening beyond static bearer token." The operator is both the "user" of the chat UI and the legally accountable party for every action the tool takes against a target, since they hold (or are relying on the tool to respect) the signed authorization for that target.

**Stakes Level:** Critical. This is not a "wrong answer is annoying" system — an LLM-generated directive that OmO dispatches without validation runs a real tool (nmap, sqlmap, Metasploit, ScoutSuite, etc.) over live SSH against a real host. A scope error here is not a UX defect; it can be unauthorized computer access.

**Output Consequence:** OmX's output (an `EngagementPlan` DAG) is not reviewed by a human before OmO executes it directive-by-directive (D-08: sequential, no approval gate between plan generation and dispatch except where `Directive.gate_required=True`). Every `target` string OmX emits becomes an argument to a real tool invocation against real infrastructure — there is no "preview and discard" step before consequence. This is the same class of stakes as an autonomous trading system or an autonomous surgical robot: the AI's output *is* the action, not a draft of one.

### What Domain Experts Evaluate Against

```
Dimension: Scope fidelity
Good: Every directive's `target` field is a member of `session.scope.targets` and not a member of `session.scope.exclusions` — verifiable by a pentester doing a line-by-line diff of the DAG against the signed scope document, with zero directives requiring interpretation ("is this subdomain in scope?") left unresolved.
Bad: A directive targets a host/subdomain/IP the operator never listed — even if it is "obviously related" (e.g. a discovered subdomain of an in-scope domain) — without a `gate_required` pause for explicit operator approval first.
Stakes: Critical
Source: Practitioner standard from penetration testing Rules of Engagement (RoE) — "the boundary between in-scope and out-of-scope assets is not technical, it's legal"; unauthorized access to a system outside the signed authorization is a CFAA (18 U.S.C. § 1030(a)(2)) violation regardless of intent or how the path was discovered.

Dimension: Stealth-level conformance
Good: Every directive's tool selection and invocation respects `session.scope.stealth_level` — e.g. a "stealth"/"low-and-slow" engagement never dispatches a directive with an aggressive full-port `nmap -T4/-T5` scan or an unthrottled brute-force tool; rate limits and timing flags match what the operator configured.
Bad: OmX or OmO dispatches a noisy/aggressive tool configuration under a stealth-constrained scope — risking IDS/IPS detection, alerting a defender mid-engagement, or (worse) disrupting a production system the operator explicitly asked to be tested carefully.
Stakes: High
Source: Practitioner methodology (PTES) — stealth/timing constraints are a first-class RoE parameter; violating them can trigger defensive countermeasures or cause denial-of-service against production infrastructure, which is itself an RoE breach independent of the CFAA question.

Dimension: Execution ordering / gate discipline
Good: A directive with `depends_on` unmet, or one that requires operator sign-off (`gate_required=True` — e.g. an exploit-phase directive following a recon/verification phase), never dispatches before its prerequisite completes and any required gate is cleared.
Bad: An exploit or intrusive directive runs before its recon/verify/approval prerequisite finishes — producing live exploitation activity the operator has not reviewed, on a target whose exposure the operator hasn't yet confirmed is real (vs. a false positive).
Stakes: Critical
Source: Practitioner standard pentest phase discipline (recon → scan → verify/gate → exploit → report) — exploiting before verification risks acting on a false-positive finding, i.e. attacking a system that was never actually vulnerable, or attacking further than authorized before confirming initial access was even legitimate.

Dimension: Failure visibility (operator awareness of what actually ran)
Good: The moment a directive's sub-agent/tool call fails, times out, or the DAG stalls, the operator sees a `PHASE_FAILED` event in the chat UI naming which directive failed and why — within the same interaction, not discovered later via a missing report section.
Bad: A directive silently fails or hangs and the engagement state shows "running"/no status change; the operator has no way to know whether a tool actually executed against the target, partially executed, or never ran — which is itself an audit/accountability gap for an activity with legal exposure.
Stakes: High
Source: This phase's own stated defect (ORCH-01) — for a system whose actions carry legal weight, "the operator can reconstruct exactly what ran, against what, and with what result" is a baseline audit requirement, not a nice-to-have UX feature.

Dimension: Plan schema validity before any tool executes
Good: OmX's generated DAG is fully validated (Pydantic schema + agent-registry membership + dependency-cycle check) before OmO dispatches directive 1 — a hallucinated agent name, invalid engine, or malformed target string is caught as a plan-validation failure, never discovered mid-DAG after side effects already occurred.
Bad: OmO dispatches directive 1, 2, 3... and only discovers directive 4 references a non-existent agent (`KeyError`) or an invalid target after earlier directives already ran real tools against the target — side effects cannot be undone by a validation failure that arrives too late.
Stakes: Critical
Source: This phase's own Critical Failure Mode #3 (malformed/hallucinated DAG dispatched as if valid) — for a system where every directive is a real action, "validate before execute" is the only correct ordering; "validate as you go" already implies partial, unauthorized execution occurred.
```

### Known Failure Modes in This Domain

1. **Scope drift via LLM inference ("helpful" over-reach)** — Claude, asked to decompose "audit acme.com," may infer and add a directive against a related-but-unlisted asset (a discovered subdomain, a linked cloud account, a third-party-hosted API) because it looks like part of the same logical target. In production pentest tooling this is the single most-cited practitioner failure mode for AI-assisted scoping — the model's notion of "complete coverage" does not know about the legal authorization boundary, and a signed RoE explicitly does not extend to infrastructure "discovered during" the engagement unless separately authorized.
2. **Stealth/aggressiveness escalation under retry or self-correction pressure** — when a directive fails or a tool times out, an LLM-driven planner or an under-constrained retry loop can "try harder" (more aggressive scan flags, higher thread counts, shorter timeouts) to get a result — silently violating the stealth-level ceiling the operator set, exactly the failure this phase's own OmX retry logic (Section 4b.1) must guard against by keeping stealth constraints in the system prompt on every retry, not just the first attempt.
3. **Exploit-before-verify ordering under sequential dispatch with no gate enforcement** — because D-08 makes OmO a strictly sequential executor with `depends_on` as the only ordering signal, a plan-validation gap that lets a `gate_required` directive slip through unblocked (or a DAG where OmX under-marks which directives should require a gate) results in exploitation tooling running against a target the operator has not yet confirmed is genuinely vulnerable — the classic "attacked a false positive" outcome practitioners specifically design verification gates to prevent.
4. **Unauthorized third-party infrastructure access via chained discovery** — a recon directive's findings (e.g. a CNAME pointing to a third-party SaaS host, a cloud resource shared with another tenant) can trigger a subsequent OmX-planned directive against infrastructure owned by an entity that is not party to the engagement's authorization — a CFAA violation distinct from and additional to a same-owner scope violation, because good intent and "it was reachable from the in-scope host" are not defenses.

### Regulatory / Compliance Context

This is not a regulated-industry deployment (no HIPAA/GDPR/FCA-style consumer-data regime applies to a single-operator internal tool), but it operates inside a real legal constraint that functions as this domain's regulatory backdrop:

- **Computer Fraud and Abuse Act, 18 U.S.C. § 1030(a)(2)** (US) / equivalent unauthorized-access statutes (e.g. UK Computer Misuse Act 1990) — accessing or exceeding authorized access to a computer system is a criminal offense. Authorization is scoped to what is documented in the engagement's signed Rules of Engagement / scope-of-work, not to what an AI planner infers as logically related. The operator, not the AI, bears legal exposure for anything the tool executes — which is precisely why Critical Failure Mode #1 (scope creep via OmX plan generation) is rated Critical rather than High: it is the one failure mode in this phase with direct legal consequence, not just engagement-quality consequence.
- **No formal Rules of Engagement document exists inside this codebase today** — `ScopeConfig` (`targets`, `exclusions`, `stealth_level`, `ports`, `protocols`) is this system's entire machine-readable representation of what a signed RoE authorizes. This means `ScopeConfig` fidelity is not a nice-to-have data model — it is the sole technical enforcement point standing between "authorized test" and "unauthorized access" for every directive OmX generates and OmO dispatches. Any gap between what `ScopeConfig` captures and what the actual signed authorization says is a gap the AI system cannot self-detect.

## 2. Framework Decision

**Selected Framework:** Hand-rolled Python (no new AI orchestration framework dependency) — extends the existing `backend/agent/llm_router.py` directly; OmX/OmO/clawhip implemented as plain Python classes calling `LLMRouter.complete()` and existing `BaseAgent` sub-agents.

**Version:** N/A (no new package) — reuses `anthropic==0.38.0` (already pinned) and adds no new orchestration-framework dependency to `backend/requirements.txt`.

**Rationale:**
This phase's dispatch model is sequential-only (locked decision D-08 in `03-CONTEXT.md`), and session persistence is already fully solved via direct SQLite + WAL mode (D-03, reusing Phase 2's pattern) independent of any orchestration framework. Every existing layer in this codebase — LLM calls, SSH execution, database access — uses direct SDK/stdlib calls with zero wrapping abstractions (`anthropic.AsyncAnthropic` directly, `paramiko` directly, `sqlite3` directly). Introducing a graph/orchestration framework here would add a new dependency and a state-schema translation layer for what is, this phase, a linear execution loop — no benefit until parallel dispatch (explicitly deferred) is in scope.

**Alternatives Considered:**

| Framework | Ruled Out Because |
|-----------|------------------|
| LangGraph | Its strengths (per-node checkpointing, time-travel debugging, native branching/parallelism) map to the explicitly *deferred* parallel-dispatch phase, not this sequential-only one — matches the framework decision matrix's own anti-pattern #7 ("Choosing LangGraph for simple linear flows — the graph overhead is not worth it"). Would also force `EngagementSession` into a `StateGraph` schema for zero functional gain given D-08. |
| CrewAI / AutoGen / Google ADK / OpenAI Agents SDK | All multi-agent frameworks assume framework-owned agent definitions; this project's `BaseAgent` ABC is an explicit, mentor-confirmed, do-not-break constraint (CLAUDE.md) — adopting any of these would mean re-platforming 12 existing sub-agents for no functional requirement in this phase. |
| LlamaIndex / Haystack | RAG/data-pipeline frameworks — this phase has no retrieval/document-Q&A component. |

**Vendor Lock-In Accepted:** No — the hand-rolled approach keeps the codebase framework-agnostic, consistent with the multi-provider LLMRouter decision (D-04) that already avoids single-provider lock-in at the model layer.

### Entry Point Pattern

**OmX — structured DAG generation via Claude forced tool use** (not free-text parsing — this is the reliable-structured-output pattern the Anthropic SDK provides today; confirmed against `anthropic-sdk-python`'s `ToolChoiceToolParam`, which sets `disable_parallel_tool_use=True` so the model emits exactly one tool call instead of prose + tool call):

```python
# backend/agent/omx.py
from pydantic import BaseModel, Field, ValidationError
from typing import Literal


class Directive(BaseModel):
    id: str
    phase: str  # "recon" | "scan" | "exploit" | "verify" | "report" | ...
    engine: Literal["InfrastructureEngine", "MLAIEngine", "ICSEngine"]
    agent: str  # must match a registered BaseAgent subclass name, validated post-parse
    target: str
    tools: list[str] = Field(default_factory=list)
    depends_on: list[str] = Field(default_factory=list)
    gate_required: bool = False


class EngagementPlan(BaseModel):
    directives: list[Directive]
    rationale: str


class OmX:
    """Workflow planner — decomposes an operator directive into an EngagementPlan DAG (D-06)."""

    def __init__(self, llm_router: "LLMRouter"):
        self.llm_router = llm_router
        # Build the tool's input_schema directly from the Pydantic model —
        # avoids hand-writing a parallel JSON schema that can drift from Directive/EngagementPlan.
        self._plan_tool = {
            "name": "emit_engagement_plan",
            "description": "Return the decomposed engagement DAG for the operator's directive.",
            "input_schema": EngagementPlan.model_json_schema(),
        }

    async def plan(self, directive_text: str, session) -> EngagementPlan:
        messages = [{"role": "user", "content": directive_text}]
        for attempt in range(3):  # 1 initial + 2 retries — see Section 4b.1
            response = await self.llm_router.claude.messages.create(
                model=self.llm_router.claude_model,  # config.settings.claude_model
                max_tokens=2048,  # sized for an ~8-directive DAG, not the 4096 chat default
                system=_OMX_PLANNING_SYSTEM_PROMPT,  # scope + vocabulary constraints, see 4b.3
                messages=messages,
                tools=[self._plan_tool],
                tool_choice={
                    "type": "tool",
                    "name": "emit_engagement_plan",
                    "disable_parallel_tool_use": True,
                },
            )
            tool_use = next(b for b in response.content if b.type == "tool_use")
            try:
                return EngagementPlan.model_validate(tool_use.input)
            except ValidationError as e:
                logger.warning(f"OmX plan validation failed (attempt {attempt + 1}/3): {e}")
                messages.append({"role": "assistant", "content": response.content})
                messages.append({
                    "role": "user",
                    "content": f"Your plan failed validation: {e}. Return a corrected plan.",
                })
        raise OmXPlanValidationError("OmX could not produce a valid plan after 3 attempts")
```

**OmO — sequential dispatch loop** (D-08: awaits each directive in DAG order, no `asyncio.gather`/`create_task`):

```python
# backend/agent/omo.py
async def dispatch(self, plan: "EngagementPlan", session: EngagementSession, agents: dict[str, BaseAgent]) -> None:
    for directive in plan.directives:  # DAG already topologically ordered by OmX; OmO does not reorder
        session.state.set_phase_status(directive.id, "running")
        agent = agents[directive.agent]  # KeyError here = pitfall #3 below, must be caught before dispatch
        try:
            result = await agent.execute(directive.target, tools=directive.tools)
            session.state.set_phase_status(directive.id, "completed")
            session.state.add_finding(result)
        except Exception as e:
            session.state.set_phase_status(directive.id, "failed")
            await self._emit_phase_failed(session.session_id, directive, e)  # via clawhip/ConnectionManager
```

| Concept | What It Is | When You Use It |
|---------|-----------|-----------------|
| Forced tool use (`tool_choice={"type": "tool", "name": ..., "disable_parallel_tool_use": True}`) | Anthropic SDK mechanism that makes Claude return exactly one structured `tool_use` block matching a given `input_schema`, instead of free-text | OmX's `plan()` call — the only reliable way to get a parseable DAG out of Claude without a prose-parsing layer |

| `LLMRouter.complete(messages, mode, system)` | Existing provider-routing facade (Claude for `mode="orchestration"`, Ollama for everything else, extended per D-04 to add `mode="compaction"`→Qwen and a configurable DeepSeek route) | OmO calls this for any non-structured LLM turn (response composition); OmX bypasses it and calls `self.llm_router.claude` directly because forced tool use needs raw SDK access `LLMRouter.complete()` doesn't expose |
| `BaseAgent.execute(target, **kwargs) -> Dict[str, Any]` | Existing ABC every sub-agent (ReconAgent, ScanAgent, ExploitAgent, ...) already implements | OmO's Executor role calls this directly per directive — no new sub-agent interface needed, per D-02/mentor-confirmed constraint |
| `EngagementState.set_phase_status(phase_id, status)` | Existing dataclass method, currently defined but never called by anything | OmO calls this once per directive transition (`running`→`completed`/`failed`) — this is the field ORCH-01's "operator sees phase failures" and PERSIST-01's "resume after restart" both read from |

### Common Pitfalls
<!-- Gotchas specific to this framework and system type — from docs, issues, and community reports -->
1. **Forgetting `disable_parallel_tool_use=True`** — without it, Claude may return the `emit_engagement_plan` tool call *plus* prose commentary, or (rarely) multiple tool calls; `next(b for b in response.content if b.type == "tool_use")` still finds a block, but downstream code that assumes `response.content[0]` (the pattern already used in `llm_router.py`'s `_claude_complete`) will silently grab the wrong block. Always filter by `.type == "tool_use"`, never index by position, when using tool_choice.
2. **`asyncio.run()` inside the WebSocket handler's already-running event loop** — `ws_handler.py`'s `websocket_chat` is itself an `async def` running inside uvicorn's loop (it already does `orchestrator = Orchestrator()` then `async for chunk in orchestrator.process_stream(...)` at line 71-77). Any OmX/OmO method reached from there must be a plain `async def` that gets `await`ed — wrapping it in `asyncio.run()` anywhere in the call chain raises `RuntimeError: asyncio.run() cannot be called from a running event loop`.
3. **`agents[directive.agent]` KeyError on a hallucinated agent name treated as a crash instead of a validation failure** — Pydantic validates `Directive.agent` as a `str`, not as `Literal[...]` of real agent names (the registry is dynamic), so a plan can pass schema validation with `agent="ReconAgennt"` (typo) and only fail at dispatch time. OmO must validate `directive.agent in agents` for every directive in the plan *before* executing directive 1, not discover it mid-DAG after directive 3 already ran side effects (ties to Critical Failure Mode #3).
4. **`sqlite3.Connection` is not thread-safe and blocks the event loop if called directly** — every read/write must go through `asyncio.to_thread(self._conn.execute, ...)` exactly as `ClientProfileDB` does; calling `self._conn.execute(...)` directly from an `async def` will silently block the entire FastAPI event loop (all concurrent WebSocket sessions, not just the current one) for the duration of the disk write.
5. **Sequential dispatch (D-08) with no per-directive timeout hangs the whole DAG** — because OmO `await`s each directive strictly in order, one sub-agent call with no timeout (e.g. `nmap` against a target that never responds) blocks every subsequent directive indefinitely with no `PHASE_FAILED` ever firing — the operator sees the engagement simply stall, which is the exact silent-failure symptom ORCH-01 exists to eliminate. Wrap each `agent.execute()` call in `asyncio.wait_for(..., timeout=...)` and treat `asyncio.TimeoutError` as a directive failure, not an unhandled exception.

## 4. Implementation Guidance

**Model Configuration:**
OmX plan generation: `config.settings.claude_model` (same Claude model already used for `mode="orchestration"`), `max_tokens=2048` (sized for an ~8-directive DAG, deliberately smaller than the 4096 chat default in `_claude_complete`), no `temperature` override (leave SDK default — plan generation benefits from the default's balance of consistency and the ability to recover from validation-retry prompts, not from forcing near-zero temperature). Compaction (D-04): Ollama/Qwen via the existing `OllamaClient`, routed through a new `mode="compaction"` on `LLMRouter.complete()`. DeepSeek: a third, optional provider wired into the same `LLMRouter.complete()` dispatch, gated by a `config.settings.deepseek_api_key` presence check so its absence never breaks orchestration or compaction.

**Core Pattern:**
Three-stage sequential pipeline per operator message, per D-01/D-02/D-06/D-08: (1) OmX.plan() — forced-tool-use call to Claude decomposes the directive into a validated `EngagementPlan` DAG; (2) OmO.dispatch() — awaits each `Directive` in DAG order, calling the matching `BaseAgent.execute()`, updating `EngagementState.phase_status`, and emitting `PHASE_FAILED` (via clawhip) the instant any directive raises or times out; (3) response composition — `ResponseComposer` (already constructed but unused in `Orchestrator.__init__`, per `03-CONTEXT.md`'s wiring-gap finding) turns the completed/failed directive results into the operator-facing chat reply, replacing the current "stream the raw Claude completion" behavior in `process_stream()`.

**Tool Use:**
OmX itself uses Anthropic's forced tool-use (`tool_choice={"type": "tool", ...}`) purely for structured output — it never invokes real security tools directly. Real tool invocation happens one layer down, inside each `BaseAgent.execute()` call that OmO dispatches to (unchanged from today — `ReconAgent`, `ScanAgent`, etc. already own their own tool lists and SSH/Kali execution). No new tool-calling surface is introduced by this phase beyond OmX's single `emit_engagement_plan` tool.

**State Management:**
Two independent stores, per D-02/D-03: (1) `EngagementState.phase_status: Dict[str, str]` (in-process, per-directive `running`/`completed`/`failed`) — OmO's only consumer today would be its first real caller; (2) `SessionStore` (SQLite + WAL, D-03) — persists the full `EngagementSession` (scope, conversation history, phase_status, findings) to disk so a backend restart can `resolve()` a session_id from disk instead of losing it. `TaskRegistry` (D-10, built for real) is the third store — directive-level handoff state (`Created`/`Running`/`Completed`) distinct from `phase_status` in that it exists to let OmO detect a directive that was dispatched but never reported a terminal status (e.g. after a crash mid-directive), which `phase_status` alone can't distinguish from "never started."

**Context Window Strategy:**
OmX's planning call is single-turn (the operator's directive text plus, on validation failure, up to 2 retry turns per the retry loop in Section 3 — never the full 40-message `ConversationHistory` window). OmO's directive dispatch calls don't touch the LLM context window at all (they call `BaseAgent.execute()` directly). The existing `conversation_summariser.py` (already in the codebase, unused by this phase's new components) remains the mechanism for keeping the operator-facing chat's 40-message window bounded — this phase adds a new, separate, short-lived planning context, not a change to that existing compaction strategy.

## 4b. AI Systems Best Practices

> Written by `gsd-ai-researcher`. Cross-cutting patterns every developer building AI systems needs — independent of framework choice.

### Structured Outputs with Pydantic

There is no framework-provided structured-output helper here (no `.with_structured_output()`, no `instructor`) — the pattern is: define the DAG schema as Pydantic models, derive the Anthropic tool's `input_schema` directly from `EngagementPlan.model_json_schema()` so the schema can never drift from the validator, force exactly one tool call via `tool_choice`, and validate the tool call's `input` against the same Pydantic model.

```python
# backend/agent/omx.py — output model + integration (see Section 3 for the full plan() method)
from pydantic import BaseModel, Field, ValidationError
from typing import Literal


class Directive(BaseModel):
    id: str
    phase: str
    engine: Literal["InfrastructureEngine", "MLAIEngine", "ICSEngine"]
    agent: str
    target: str
    tools: list[str] = Field(default_factory=list)
    depends_on: list[str] = Field(default_factory=list)
    gate_required: bool = False


class EngagementPlan(BaseModel):
    directives: list[Directive]
    rationale: str
```

**Framework integration:** the Anthropic SDK has no `response_format`/`with_structured_output` convenience for the pinned `anthropic==0.38.0`; the reliable pattern is forced tool use — `tools=[{"name": "emit_engagement_plan", "input_schema": EngagementPlan.model_json_schema()}]` + `tool_choice={"type": "tool", "name": "emit_engagement_plan", "disable_parallel_tool_use": True}` — then `EngagementPlan.model_validate(tool_use_block.input)`.

**Retry logic:** up to 2 retries (3 attempts total). On `pydantic.ValidationError`, log at `WARNING` with the validation error text and the attempt number (never log the raw target/credentials from the failed plan at `INFO` or above — matches this codebase's existing "never logged" `CredentialVault` discipline); append the model's own malformed output plus a corrective instruction ("Your plan failed validation: {e}. Return a corrected plan.") as the next turn, so Claude self-corrects with the exact schema error in context. If all 3 attempts fail, raise `OmXPlanValidationError` and surface it to the operator as a `PHASE_FAILED`-style chat message — never fall back to executing a partially-parsed or default plan (this is Critical Failure Mode #3 in Section 1).

### Async-First Design

Every layer this phase touches is already `async def` — `LLMRouter.complete()`, `BaseAgent.execute()`, `ws_handler.py`'s `websocket_chat`, `SessionStore` (once SQLite-backed). OmX's `plan()` and OmO's `dispatch()` must follow the same convention: plain `async def`, called with `await` from wherever `Orchestrator`/`ws_handler.py` already instantiates and awaits `Orchestrator.process_stream()` today (line 73 of `ws_handler.py`).

**The one common mistake:** calling `asyncio.run(...)` anywhere in the OmX/OmO call chain. `websocket_chat` in `ws_handler.py` is itself running inside uvicorn's already-active event loop (`async for message in websocket.iter_json():` at line 44) — `asyncio.run()` nested inside that raises `RuntimeError: asyncio.run() cannot be called from a running event loop`. There is no legitimate reason to call it anywhere in this phase's code; if a helper script or test harness needs a fresh loop, that belongs in the entrypoint (`backend/app.py`'s `uvicorn.run()`) or a test's own `asyncio.run()`, never inside request-handling code.

**Stream vs. await:** OmX's DAG-generation call must always be a blocking `await` — forced tool use with `disable_parallel_tool_use=True` returns one complete `tool_use` block; there is nothing meaningful to stream token-by-token before the JSON is whole, and partial JSON can't be validated against `EngagementPlan` mid-stream. OmO's post-directive response composition (narrating "ReconAgent found 3 open ports" back to the operator) is the opposite case — that's exactly what `Orchestrator.process_stream()`'s word-by-word `yield` already does, and should keep doing, for UI responsiveness.

### Prompt Engineering Discipline

**System vs. user separation:** `orchestrator.py`'s `_SYSTEM_PROMPT` constant is for conversational replies only — OmX's planning call needs its own dedicated `_OMX_PLANNING_SYSTEM_PROMPT` (do not reuse `_SYSTEM_PROMPT`) that states: the operator's approved `session.scope.targets`/`exclusions`/`stealth_level` as hard constraints, and the closed vocabulary of valid `engine` values (`InfrastructureEngine`/`MLAIEngine`/`ICSEngine`) and registered agent names — reducing (not eliminating; see pitfall #3 in Section 3) hallucinated directive fields. The operator's raw directive text (e.g. `"$pentest acme.com"`) stays in the `user` turn, unmodified.

**Few-shot — inline, not dynamically retrieved:** the 7 planning-keyword workflows (`$pentest`, `$cloud-audit`, `$genai-probe`, `$recon`, `$scope-discover`, `$iam-audit`, `$endpoint` — `OPTIMUS_PRIME_ARCHITECTURE.md` §3.1) are a small, fixed, versioned-in-code set. Embed the canonical `$pentest` 8-phase decomposition directly as a static few-shot example in `_OMX_PLANNING_SYSTEM_PROMPT`. A retrieval step (vector search over past plans) would be pure overhead for 7 known templates — reconsider only if the workflow-keyword set grows into the dozens.

**`max_tokens` — explicit, sized per call type, never reused blindly:** `LLMRouter._claude_complete()` currently hardcodes `max_tokens=4096` for every call regardless of `mode` (`llm_router.py` line 41). OmX's `plan()` call should set its own explicit, smaller `max_tokens=2048` (sized for an ~8-directive JSON DAG) rather than inheriting the chat default — and a tool_use response whose `stop_reason == "max_tokens"` must be treated as a validation failure (truncated JSON) that triggers the retry path above, not parsed as if complete.

### Context Window Management

This is the Multi-Agent case: summarisation, not RAG chunking. `ConversationHistory.get_context_window()` today is a hard slice of the last 40 raw messages (`engagement_session.py` line 27) — for an 8+ directive engagement, raw tool output (full `nmap`/`nikto` stdout) dumped into `conv_history` would both blow past useful context fast and pollute OmX's next planning call with irrelevant noise. Pattern: after each directive completes in `OmO.dispatch()`, route the directive's raw finding/tool output through the existing `conversation_summariser.py` (mode `"compaction"` → Ollama/Qwen per D-04) before calling `conv_history.add_message(...)` — only the compacted summary enters the token-bounded chat history that both the operator-facing reply and any subsequent OmX planning call will read. Separately, the DAG itself (potentially a dozen structured directives with tool lists) belongs in `EngagementState`/`TaskRegistry`, not re-injected wholesale into `conv_history` on every turn — only the active directive's status and the plan's `rationale` string need to be in context for follow-up operator messages; the full DAG detail is state, not chat history.

### Cost and Latency Budget

**Per-call estimate:** OmX's `plan()` runs once per operator directive (not once per sub-agent step) on `claude-sonnet-4-6` — roughly 1-2K input tokens (system prompt + few-shot + `conv_history` window) and up to 2K output tokens (the DAG JSON, capped by `max_tokens=2048` above). Budgeting for a ~15% structured-output validation-failure rate on the first attempt (retries per Section 4b.1), a full 8-phase engagement should cost **2-4 Claude calls total for planning** — directive *dispatch* itself makes zero additional LLM calls (`EngineRouter.dispatch()` is regex-based, `InstructionParser` is regex-based, sub-agent `execute()` calls tools directly over SSH, not the LLM).

**Caching:** exact-match only, keyed on `(operator_message_text, hash(session.scope))` — if the operator re-issues an identical directive in the same session (e.g. re-running `"$pentest acme.com"` after tweaking nothing), reuse the last validated `EngagementPlan` instead of a fresh OmX call. Semantic/embedding-based caching is not worth the added dependency and latency here — this is a single-operator, personal-use system (per `CLAUDE.md`), not a shared multi-tenant service with cache-hit volume to amortize embedding cost against.

**Cheaper models for sub-tasks:** route the context-compaction summarisation in Section 4b's "Context Window Management" through `LLMRouter.complete(mode="compaction")` → Ollama/Qwen (local, zero marginal API cost) per D-04, never Claude. Intra-directive routing (which engine, which agent) stays on the existing zero-cost regex path (`EngineRouter.dispatch()`, `InstructionParser._detect_intent()`) — it is already free and already correct for this; the only call that needs Claude's full reasoning is the DAG-decomposition itself (D-06, explicitly required to be LLM-driven, not template-matched).

### Dimensions

## 6. Guardrails

> No traditional customer-facing "online guardrail" applies — there is no production user base to filter for. The equivalent concept here is a **pre-execution validation gate**: a synchronous, blocking check that runs between OmX plan generation and OmO's first `agent.execute()` call, before any directive can have a real-world side effect. These are kept minimal per Section 1b — every gate here maps directly to one of the five Critical Failure Modes, none are speculative.

### Online (Real-Time) — Pre-Execution Validation Gates

| Guardrail | Trigger | Intervention |
|-----------|---------|---------------|
| Scope-membership gate | Any `directive.target` not in `scope.targets`, or present in `scope.exclusions` | **Block** — plan validation fails before directive 1 dispatches; surfaced to the operator as a rejection (same delivery path as `PHASE_FAILED`); the plan never enters `OmO.dispatch()` |
| Plan schema / agent-registry / cycle gate | `EngagementPlan` fails Pydantic validation, references an unregistered `agent`, or the `depends_on` graph has a cycle | **Block** — OmX retries up to 3 attempts total (Section 4b.1); after 3 failed attempts, raise `OmXPlanValidationError` and surface it to the operator — never dispatch a partially-valid plan |
| Gate-required / unmet-dependency check | A directive with `gate_required=True` or an unmet `depends_on` reaches the front of OmO's dispatch loop | **Block** — dispatch pauses; `agent.execute()` is not called for that directive until prerequisites read `"completed"` and (for gated directives) an explicit operator-approval signal is received |
| Stealth-tier tool/flag check | A directive's tool invocation includes a flag/config outside the `stealth_level` allowlist | **Block** — directive rejected pre-execute, surfaced via the same `PHASE_FAILED`-style path |
| Per-directive execution timeout | `agent.execute()` exceeds a configured wall-clock timeout (`asyncio.wait_for`) | **Escalate** — treated as a directive failure, `PHASE_FAILED` emitted; the sequential dispatch loop halts on that directive rather than hanging indefinitely (Section 3 pitfall #5) |

### Offline (Flywheel)

| Metric | Sampling Strategy | Action on Degradation |
|--------|--------------------|--------------------------|
| DAG decomposition quality (LLM-judge score vs. canonical template, dimension 7) | **Full review** — every OmX `plan()` call, not sampled (low volume: ~2–4 calls per engagement, single operator) | Judge score drops or disagrees with the operator's own read → add the case to the reference dataset and retune `_OMX_PLANNING_SYSTEM_PROMPT`'s few-shot example |
| Scope-fidelity near-misses (`gate_required` trigger rate per workflow keyword) | Full review — every gated directive logged to the XAI audit trail | A gate-trigger rate trending toward zero over time is a **degradation signal, not a success signal** — investigate for prompt under-gating (silent over-trust) before treating it as "the system got better" |
| Retry/self-correction drift (Known Failure Mode #2) | Full review — every OmX validation-failure retry | If a retry "fixes" a validation failure by loosening stealth/tool aggressiveness rather than correcting the schema/scope error, flag for operator review immediately — this is the exact escalation-under-retry-pressure pattern Section 1b warns about |
| Session persistence integrity (dimension 6) | Full review — every backend restart event (naturally low-frequency for personal use) | Any `phase_status`/finding mismatch on resume is treated as P1: halt further engagement dispatch and surface to the operator; never auto-resume past an unverified state |

## 7. Production Monitoring

**Tracing Tool:** The existing `ExplainableAI` audit log (`backend/reporting/explainable_ai.py`) — extended to persist to SQLite using the same WAL pattern as `SessionStore` (DATA-01/D-03), rather than adopting a new observability platform. This is a deliberate choice, not an oversight: D-09 already requires clawhip to deliver decision/lifecycle events to "the XAI audit trail," so the mandated audit trail and this phase's eval/monitoring trace are the same artifact — building a second system (Arize Phoenix, Langfuse) to duplicate it would be pure overhead for a single-operator system generating a handful of traces per engagement. **Escalation path, not adopted now:** if trace volume or replay/visualization needs grow materially (e.g. future multi-target or parallel-dispatch phases), Arize Phoenix (open-source, self-hostable, OpenTelemetry-based) is the recommended next step — revisit if `ExplainableAI`'s flat SQLite log stops being enough to answer "what did the system decide and why" by hand.

**Key Metrics to Track:**
1. **`PHASE_FAILED` emission latency** — time between the underlying exception/timeout and WebSocket event delivery; should be near-instant. A regression here silently reintroduces ORCH-01, the defect this phase exists to fix.
2. **Plan-validation retry distribution** (attempt 1 vs. 2 vs. 3, Section 4b.1's 3-attempt budget) — a trend toward attempt 3 / `OmXPlanValidationError` signals prompt drift or a gap in the scope/vocabulary constraints in `_OMX_PLANNING_SYSTEM_PROMPT`.
3. **`gate_required` trigger rate per workflow keyword** — tracks scope-fidelity health; see the offline flywheel row above for interpretation (falling rate is a signal to investigate, not celebrate).
4. **Session resume integrity** (`phase_status`/finding match rate after a restart) — should be 100%; any miss is P1.
5. **Provider routing distribution** (orchestration→Claude count vs. compaction→Ollama count vs. any unexpected fallback) — confirms ORCH-02's multi-provider routing is behaving as configured without needing a full cost-tracking platform.

**Alert Thresholds:** This is a single-operator, personal-use system with no on-call — "alert" means a `WARNING`/`ERROR`-level log line the operator sees in the terminal/log file, not a paging system.
- Plan validation reaching attempt 3 (`OmXPlanValidationError` raised) → `WARNING` logged, surfaced immediately as a `PHASE_FAILED`-style chat message (already required behavior, not an additional feature)
- Any scope-membership gate rejection → `WARNING` logged with full directive detail — never silently dropped (Critical Failure Mode #1 is the one failure mode in this phase with direct legal exposure)
- Any session-resume mismatch → `ERROR` logged, engagement dispatch halted until the operator confirms state
- Any per-directive timeout fired → `WARNING` logged naming the directive and elapsed time

**Smart Sampling Strategy:** Given personal-use call volume (a handful of engagements per week, ~2–4 OmX `plan()` calls each), sampling is unnecessary — **review 100%** of: (a) every `gate_required` trigger, (b) every plan-validation retry, (c) every `PHASE_FAILED` event. Standard signal-based sampling (weighting toward retries, escalations, unusual output length) only becomes relevant if usage volume grows enough that full review stops being practical — noted here as a future revisit trigger, not something to build now.
