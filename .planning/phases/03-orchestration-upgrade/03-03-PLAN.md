Make EngagementSession durable across a backend restart (PERSIST-01): add serialization to EngagementSession, convert SessionStore to a SQLite + WAL cache-plus-persistence store reusing Phase 2's established pattern, and add `await` to the now-async SessionStore call sites in ws_handler.py.

Output: durable SessionStore, serializable EngagementSession, updated ws_handler call sites, extended persistence tests.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| in-memory session ↔ SQLite (disk) | Session state crosses a persistence boundary; a crash mid-write introduces on-disk/in-memory divergence |
| WAL file on disk | New on-disk attack surface (WAL/-shm files, crash-recovery reads) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-05 | Tampering / Repudiation | SessionStore SQLite persistence | mitigate | Reuse Phase 2's proven WAL pattern (journal_mode=WAL, synchronous=NORMAL reissued per connect); single-statement writes are atomic under WAL; do not invent a new persistence scheme (per phase threat guidance) |
| T-03-05b | Information Disclosure | sessions.db at rest | accept | SQLite files unencrypted at rest, consistent with existing ClientProfileDB/ResearchKB precedent; single-operator local machine, no new regression |
| T-03-SC | Tampering | package installs | accept | No package installs this phase (stdlib sqlite3/asyncio only) |
</threat_model>
